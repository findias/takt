# Контекст проекта для Codex

Проект — **Такт / Takt**, канбан-трекер для частной установки примерно
на 130 пользователей. Публичный репозиторий: `findias/takt`, основная
ветка — `master`. Название рабочего каталога `agile` историческое.

## Перед работой

1. Прочитать `CLAUDE.md`: это основной уклад проекта, он действует
   и при работе через Codex. Не заводить здесь вторую копию его правил.
2. Прочитать `PROJECT_MEMORY.md`: перенесённый из памяти Claude контекст,
   договорённости владельца и важные причины решений.
3. Состояние задач проверять в `ROADMAP.md`, работу над UI — в `UI-PLAN.md`.
   Это ссылки на файлы за пределами публичного репозитория. Если ссылки
   недоступны, сказать об этом; старую запись памяти не считать планом.
4. Для изменения интерфейса прочитать подходящие локальные скиллы:
   `.claude/skills/board-design/SKILL.md`,
   `.claude/skills/frontend-ui/SKILL.md`,
   `.claude/skills/frontend-react/SKILL.md`,
   `.claude/skills/frontend-perf/SKILL.md`.
   Эти локальные скиллы не входят в публичный Git-клон. При их отсутствии
   опираться на `CLAUDE.md`, `CONTRIBUTING.md`, `PROJECT_MEMORY.md`
   и существующие компоненты; не утверждать, что отсутствующие файлы прочитаны.

Текущие указания пользователя и инструкции среды имеют приоритет.
Записи о прежних инструментах Claude не означают, что эти инструменты
или доступы есть у Codex.

## Как работать с владельцем

- Общаться по-русски, коротко и предметно. Завершать порученный срез
  целиком; не останавливаться на плане или предложении продолжить.
- Не запускать субагентов без прямого запроса владельца. Беречь токены,
  использовать уже сделанные исследования.
- «Добавь в план» означает записать обсуждённое в `ROADMAP.md` с причиной
  и оговорками. «Продолжай» относится к текущему обсуждаемому плану;
  следующий пункт определять по самому плану.
- Не создавать HTML-разборы и новые страницы исследований по собственной
  инициативе. Результат проверки — текстом; рабочие планы — в плане.
- Публичный код и примеры должны оставаться универсальными: без названий
  внутренних систем заказчика, частных доступов и инфраструктурных секретов.
- Не запускать Prettier: в проекте нет его конфигурации. Сохранять
  существующее оформление и не переформатировать файлы целиком.

## Опорные команды и ограничения

- `make check` — обязательная общая проверка: gofmt, vet, vet с `load`,
  Go-тесты с PostgreSQL, TypeScript и тесты клиента.
- `go test -short ./...` — явно сокращённый прогон. Обычный `go test ./...`
  без `TEST_DATABASE_URL` намеренно падает, а не молча пропускает базу.
  `make test` запускает этот сокращённый прогон без базы.
- `make stand` **удаляет dev-базу**. Для проверки существующего проекта
  предпочитать отдельную тестовую базу; `make demo` добавляет демо-данные.
- `make run` пересобирает клиент; `make check` сборку `web/dist` не делает.
  После изменения Go перезапустить сервер. Проверять процессы по PID,
  не завершать их широким `pkill -f`.
- Схему менять только новой миграцией, совместимой с предыдущим бинарником.
  Подробности про RLS, перенос данных и проверки — в `CLAUDE.md`.
- Любая фича сразу на русском и английском, с документацией на обоих
  языках и обновлением сгенерированных страниц через `make docs`.
- После изменения вёрстки смотреть свежие снимки обоих языков, включая
  состояния, которых нет в штатном наборе. Зелёные тесты не заменяют
  проверку координат и реальной раскладки.
- Коммиты: английский заголовок и тело с `How to check:`, затем
  `--- ru ---` и русский перевод с `Как проверить:`. Не добавлять
  подписи модели и ссылки на сеансы. Не отключать GPG-подпись без
  указания владельца. Сам перенос контекста не является поручением
  на commit, push или выпуск.

## Поддержание памяти

`PROJECT_MEMORY.md` хранит устойчивый контекст и причины решений,
а не копию незакрытых задач или актуальной ветки. При расхождении
проверить код, миграции, сообщения коммитов и рабочие планы.
Датированные результаты начальной проверки — в `PROJECT_REVIEW.md`.
